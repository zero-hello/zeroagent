# ADR-001：保留生命週期的聊天核心責任拆分

## 狀態

採用於 `refactor/chat-core-architecture` 工作分支，尚不代表遠端 main 或正式版本已採用。

## 日期

2026-10-18

## 背景

ChatService 原有 3,818 行，GenerationLoop 原有 1,982 行，工具核准、串流儲存及壓縮跨越多種生命週期。單純依行數搬移方法會保留理解成本，全面重新設計則可能改變取消、恢復、核准與資料保存語義。另有兩條已驗證但尚需整合的聊天／權限分支。

## 決策

先合併兩條來源歷史並跑整合驗證。維持 ChatService 公開入口及 session／scope，抽出串流持久化協調、摘要生成、通知、模型請求與工具批次執行等責任。新元件以必要型別及小量回呼接線，不建立全專案通用 pipeline 或為每個 repository 再包一層 interface。

dirty marker、節流與持久化鎖由同一協調器擁有，明確保存與串流寫入使用同一把鎖。工具執行仍在原 Flow／run owner 中依序進行，標記與結果透過 suspend 回呼回到原有訊息發送位置。壓縮的觸發與生命週期先留在服務，摘要生成獨立。

## 考慮過的選項

- 只把 helper 移到多個 extension 檔案：行數減少但狀態與依賴仍隱藏，不足以降低修改成本。
- 全面改成新的狀態機及多個 Gradle module：有機會更徹底隔離，但在維持行為的本輪範圍內，風險與驗證面過大。
- 按責任增量抽出：保留既有 API 與測試，先對併發邊界補回歸，之後依修改熱點再整理剩餘協調流程。

## 後果

核心入口縮短，Agent 可按任務只讀單一責任及相關測試。服務仍保有較多協調工作，這是本輪選擇的邊界；後續拆 session／compaction orchestration 必須另行保護鎖與生命週期。大型設定／診斷／Web UI 檔案仍待後續整理。模組數、資料庫 schema、產品版本與正式發布流程不因本輪改動而改變。
